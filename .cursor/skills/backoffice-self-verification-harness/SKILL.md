# Backoffice Codex Self-Verification Harness

## 목적

변경한 코드가 의도한 경로에서 동작하고 인접 기능을 깨뜨리지 않았다는 증거를 만든다. 체크리스트를 기계적으로 소진하는 것이 아니라 `변경 → 영향 → 검증 → 증거`를 연결한다.

## 기본 원칙

- 구현을 시작하기 전에 성공 조건과 주요 실패 경로를 정한다.
- 변경 범위와 위험에 비례한 최소 충분 검증을 선택한다.
- 빠르고 좁은 검사부터 실행하고 통과한 뒤 넓은 검증으로 진행한다.
- 명령의 종료 코드와 실제 출력으로 판단한다. 스크립트의 성공 문구만 신뢰하지 않는다.
- 실패를 숨기거나 추정으로 통과 처리하지 않는다.
- 기존 실패로 판단할 때는 변경 전 상태, 관련 없는 파일, 동일 실패의 재현 등 근거를 제시한다.
- DB 초기화, 데이터 삭제, 외부 전송 같은 파괴적 검증은 별도 승인 없이 실행하지 않는다.

## 1. 변경 전 기준선

1. `git status --short`로 기존 사용자 변경을 기록한다.
2. 대상 route, Controller, Request, Service, Model, Blade, CSS, JavaScript, 테스트의 연결을 검색한다.
3. 아래 형식으로 검증 지도를 만든다.

| 변경 | 영향 가능 경로 | 실패 신호 | 검증 |
|---|---|---|---|
| 예: 목록 필터 | query string, pagination, 복귀 URL | 필터 초기화 | 대상 테스트 + 브라우저 왕복 |

작은 변경은 표를 문서로 만들 필요 없이 내부 작업 메모로 유지해도 된다.

## 2. 정적 검증

변경 파일에 해당하는 검사만 실행한다.

### PHP

```bash
php -l path/to/changed.php
```

Sail이 실행 중이면 다음 형태를 우선한다.

```bash
./vendor/bin/sail php -l path/to/changed.php
```

### Blade 및 자산 분리

변경한 Blade 범위에서 새 인라인 코드가 없는지 확인한다.

```bash
rg -n 'style=|onclick=|<style|<script' resources/views/path/to/changed
```

검색 결과가 기존 코드라면 새로 추가된 것인지 diff와 대조한다.

### 연결 정합성

- route 이름과 HTTP method
- Controller 메서드와 Form Request
- 폼 action 및 redirect 대상
- JavaScript endpoint와 응답 형식
- Model fillable/cast/relationship 사용처

`rg`와 `git diff --check`를 사용해 실제 참조와 공백 오류를 확인한다.

## 3. 자동화 검증

가장 가까운 테스트부터 실행한다.

```bash
./vendor/bin/sail artisan test --filter=RelevantTest
```

대상 테스트가 없으면 관련 테스트 파일 또는 디렉터리 단위로 실행한다. 전체 테스트는 공통 계층, 인증, 권한, 라우팅처럼 영향 범위가 넓거나 대상 테스트 통과 후 추가 확신이 필요할 때 실행한다.

검증 중 테스트를 새로 작성했다면 다음을 확인한다.

- 정상 경로만이 아니라 유효성 실패 또는 권한 실패가 포함되는가
- 구현 세부사항이 아니라 외부 동작을 검증하는가
- 테스트 데이터가 다른 테스트와 독립적인가

## 4. 변경 유형별 런타임 시나리오

### CRUD

- 목록 → 생성/수정 → 저장 → 목록 복귀
- 취소와 유효성 실패 후 입력값 보존
- 삭제 또는 상태 변경 후 수치·정렬·플래시 메시지 반영

### 필터와 목록

- keyword, 기간, per_page, pagination 조합
- 수정 화면 진입 후 목록 복귀 시 query string 유지
- 빈 결과, 첫 페이지, 마지막 페이지 경계

### 인증과 권한

- 허용 사용자 성공
- 미인증 사용자 처리
- 권한 없는 사용자 거부
- 세션 만료 또는 CSRF 실패 경로

### 공통 UI·JavaScript

- 변경한 화면과 다른 도메인의 소비 화면 최소 1곳
- 중복 제출, 처리 중 상태 고착, 오류 후 버튼 복구
- 브라우저 콘솔 오류와 실패 네트워크 요청

런타임 확인이 불가능하면 가능한 정적·자동화 검증을 먼저 끝내고 미실행 사유와 재현 절차를 보고한다.

## 5. 데이터베이스 변경 검증

- 마이그레이션 파일의 `up` 동작, 인덱스, FK, nullable/default를 검토한다.
- 운영 데이터가 존재할 수 있으면 rollback 가능성보다 전방 호환성과 데이터 보존을 우선한다.
- 시더의 반복 실행 가능성과 삭제 쿼리를 확인한다.
- 실제 `migrate`, `seed`, rollback 계열 실행은 사용자 승인 범위 안에서만 수행한다.

## 6. 완료 판정

다음을 모두 만족해야 완료로 보고한다.

- 요청한 동작이 구현되었다.
- 변경 파일의 diff를 다시 읽었다.
- 선택한 정적 검사와 대상 테스트가 통과했다.
- 고위험 경로를 실행했거나 미실행 이유와 재검증 방법을 남겼다.
- 기존 사용자 변경을 덮어쓰지 않았다.

## 최종 보고 형식

```text
결과: 구현된 사용자 관점의 변화
변경: 주요 파일과 책임
검증:
- [통과/실패] 실행 명령 또는 시나리오 — 핵심 결과
미실행/잔여 위험:
- 항목 — 사유 — 재검증 방법
```

검증 항목이 없다는 표현은 사용하지 않는다. 최소한 diff 검토와 변경 파일에 맞는 정적 검사는 수행한다.
